## 2A. Security flaws  **NEW (4th scan)**
This is a local desktop app with one till, so the main risks are a curious or careless person at the till, a lost computer or USB stick, and mistakes that lock the shop out. Related items found earlier:
bug 2.2 (default admin password stays usable), bug 2.3 (unlimited discounts), bug 2.12 (password hash strength), edge case 3.8 (any employee can empty a table) and feature 4.2 (audit log).

1. [ ] **[Med] CSV export can run a formula in Excel.** `ReportWindow.csv()` only quotes commas, quotes and line breaks. A product named `=HYPERLINK("http://...")` or starting with `+`, `-` or `@` becomes a live formula when the report is opened in Excel.
       Prefix such cells with an apostrophe or a space (and treat a leading tab or carriage return the same way). Add a test. **(confirmed in code)** **Reproduced in the 6th scan:** `csv()` returned `=HYPERLINK(...)`, `+1+1`, `@SUM(A1)` and `-2+3` unchanged (only the first got quotes, from its inner double quotes); a value with a bare carriage return (`a\rb`) is not quoted either.
2. [ ] **[Med] The "last admin" rule can be beaten.** The check (`countActiveAdmins() <= 1`) lives in the screen, then `UserDAO.updateStatus` / `updateRole` run as a separate step with no guard. Two admins working at once can lock or demote each other and leave no active admin,
       and the only way back in is editing the database by hand. Enforce it in the DAO in one transaction (for example `UPDATE ... WHERE (SELECT COUNT(*) FROM users WHERE role='ADMIN' AND status='ACTIVE') > 1`) and test it. **(confirmed in code)**
3. [ ] **[Med] Permissions are checked only in the screens.** `requireAdmin()` and `Session.isAdmin()` sit in controllers; `OrderDAO.cancelPaidOrder`, `UserDAO.updateRole`, `updatePasswordHash`, `ProductDAO.update` and the backup code check nothing. One forgotten check in a future handler exposes the action.
       Add a small permission check in the service layer (see 6.5 and 6.21). Also, employees can open the accounts list read-only and see every staff username and phone number; decide whether that is wanted. **(confirmed)**
4. [ ] **[Med] Customer data and password hashes are stored and backed up in plain form.** The database holds customer names and phone numbers and every PBKDF2 hash, and the backup button copies all of it to any folder or USB stick with no warning.
       Add a warning in the backup dialog, offer a passphrase-protected backup, keep the live database readable only by the shop's Windows user, and note that moving data into the project folder (1.3) makes the exposure larger.
       Customers are never told their phone number is stored and cannot ask for removal (feature 4.8); Vietnam has a personal-data decree, so ask an adviser what notice or consent the shop needs. **(confirmed for the storage; the legal part is for an adviser)**
5. [ ] **[Med] The default password is built into the program.** On any empty database `seedDefaultAdmin` creates `admin` with the known password `Admin@123`. Deleting or moving `lunavera.db` therefore resets the shop to a known login, and anyone who has read the source or the notes knows it.
       Better: on first launch ask the owner to choose the admin password and never create a default one (this goes together with bug 2.2 and the first-run setup, feature 4.15). **(confirmed)**
6. [ ] **[Med] No dependency or build-supply-chain checks.** The Maven wrapper is pinned to Maven 3.8.5 (2022) and has no `distributionSha256Sum`/`wrapperSha256Sum`; dependency versions are fixed by hand (see 6.20) and nothing scans them for known vulnerabilities.
       Update the wrapper and add the checksums, add the OWASP dependency-check plugin (or GitHub Dependabot alerts) to the CI in 6.1, and sign the Windows installer once one exists, so users are not told to ignore SmartScreen warnings. **(confirmed for the wrapper; the rest is a practice)**
7. [ ] **[Low] Anyone at the login screen can lock the admin out for 30 seconds.** `LoginThrottle` counts wrong tries per typed name, so five wrong passwords for `admin` block the real admin, and this can be repeated. For a till behind a counter this is acceptable, but choose on purpose:
       add a growing delay only for wrong passwords (a correct password still gets in), or keep the block and show the admin who is being blocked. **(confirmed by reading)**
8. [ ] **[Low] Product pictures are copied without any check.** `ImageStorage.storeNewFile` accepts any file the picker returns, of any size; the extension filter is only a hint in the file dialog. Reject files over about 5 MB, check that the file really is a PNG or JPEG
       (first bytes) and read its dimensions before copying, so a huge or damaged picture cannot freeze the screen (extends edge case 3.12 and request 1.2). **(confirmed in code)**
9. [ ] **[Low] Security events are not logged.** Failed logins, lockouts, password resets, role changes and account locks leave no log line (`AuthenticationService` has no logger). Log them (never the password) until the audit log in 4.2 exists. **(confirmed)**
10. [ ] **[Low] An open session keeps working after its password is reset.** A cashier logged in on another screen carries on after an admin resets or changes that account's password; only a lock or deletion ends the session (checked every 30 s, with the gap in 3.14).
        Store a "password changed at" value and let `SessionGuard` end sessions older than it. **(confirmed)**
11. [ ] **[Low] Passwords stay in memory.** Passwords are held as `String`, and `PBEKeySpec` is never cleared (`spec.clearPassword()`). Little value on a desktop, but a one-line fix in `PasswordUtil`. **(confirmed)**

12. [ ] **[High] The backup button can destroy the database it is meant to protect.** **NEW (5th scan)** See bug 2.23 (reproduced). Listed here too because it is a data-loss hole reachable by an ordinary admin with one wrong click.
13. [ ] **[Low] A stored password hash can make the login hang.** **NEW (5th scan)** `PasswordUtil` reads the iteration count from the stored value and uses it as is. A damaged or hand-edited hash with a huge number (for example `99999999`) keeps a login thread busy for minutes.
        Anyone who can edit the database can do worse, so this is hygiene: when verifying, reject a count outside a sane range (say 10,000 to 5,000,000) as a failed login and log it. Add a test. **Reproduced in the 6th scan:** a stored count of 20,000,000 made one login take **21 s** (the normal 120,000 takes 0.15 s here), so 99,999,999 would be about 105 s. Counts of 0, -1 and 1 are rejected as a failed login, so my first note about "accepted" was wrong.
14. [ ] **[Low] Logs are readable by every user of the PC and may hold personal data later.** **NEW (5th scan)** At the moment the log lines I searched do not contain phone numbers or names, which is good. Keep it that way (a rule in 6.x: never log customer fields or amounts tied to a person), and when the data folder moves (1.3) set the folder so only the shop's Windows user can read it. **(confirmed for today's lines; the rule is for the future)**
15. [ ] **[Med] Data stays on screen after logout.** **NEW (6th scan)** See bug 2.30: the sales report and the order history (customer names, totals) can remain open on a shared till after the person logged out. **(confirmed by code search)**
16. [ ] **[Low] Errors are shown with internal wording.** **NEW (6th scan)** Beyond item 5.15: `AlertUtil.error(... e.getMessage())` also shows file paths and SQL-driver text (for example the backup failure I reproduced: `[SQLITE_CANTOPEN] Unable to open the database file (unable to open database: C:\Users\...)`). On a shared till that tells a curious person where the data lives. Show a short Vietnamese message and log the detail. **(reproduced for the backup message)**

## 3. Niche and edge cases (most important first)
1. [ ] **Stock is only taken at payment.** Two open tables can both hold the last item and the second payment fails at the end; the product list on screen is
       also loaded once and can be out of date. Consider reserving stock when a line is added, or re-checking stock before the payment dialog. **(confirmed)**
2. [ ] **Editing a product can overwrite sales.** **NEW (2nd scan)** `ProductDAO.update` writes `stock = ?` with the number that was in the edit dialog. If a sale (another window, or a payment while the dialog is open)
       changes the stock after the dialog opened, saving the dialog puts the old number back and the sold items reappear. Fix: save stock changes as a difference
       (`stock = stock + ?`) or compare with the stock read when the dialog opened, and warn on a mismatch. **(confirmed)** **Reproduced in the 6th scan:** stock 10, a sale of 3 (stock 7), then saving a product object loaded before the sale (only the name changed) put the stock back to **10**.
3. [ ] **Two copies of the app on the same database.** There is no single-instance lock, so a double-click opens a second window on the same SQLite file. **(confirmed)**
4. [ ] **Customers can never be deleted or merged.** **NEW (2nd scan)** By design (past orders point to them), but a duplicate or a customer who asks to be removed cannot be handled in the app. See feature 4.8. **(confirmed)**
5. [ ] **A sale that crosses midnight** shows under different days in the order history (created date) and the report/dashboard (paid date). Decide one rule and say so on screen. **(confirmed)**
6. [ ] **Only Vietnamese phone numbers are accepted** (`0…`, `84…`, `+84…`); a foreign customer's number is rejected. **(confirmed)**
7. [ ] **Cancelling a paid order after points were spent** takes points down to a floor of 0, so a customer can keep more than they earned. **(confirmed)**
8. [ ] **Any employee can empty a table and so cancel another cashier's unpaid order.** **NEW (2nd scan)** There is a confirm dialog but I found no role check in `OrderController.handleToggleTableStatus`, and nothing records who did it
       (see feature 4.2, audit log). **(confirmed for the code path; intended policy is the owner's call)**
9. [ ] **Customers who give a name but no phone** get no loyalty points and cannot be found later. By design, but staff may not know. Say so near the phone field. **(confirmed)**
10. [ ] **Order times use the computer's local clock.** A wrong system date puts orders on the wrong day. **(inferred)**
11. [ ] **Product price changed while an order is open:** lines already in the cart keep the old price. Probably right; decide it on purpose. **(confirmed)**
12. [ ] **Product pictures are not checked** for size or real image content, only the file extension filter. **(inferred)**
13. [ ] **[Med] Cancelling a paid order changes an earlier day's totals.** **NEW (3rd scan)** `ReportDAO` counts revenue by the `paid_at` day and only for status `PAID`. A sale cancelled today but paid last week disappears from last week's
        revenue, after that week's cash was already counted, and no refund date is stored, so today shows nothing. Decide the rule (refunds count on the day they were made is the usual one) and store `cancelled_at` (see feature 4.2). **(confirmed by reading the queries)**
14. [ ] **[Low] The session check pauses while another window is open.** **NEW (3rd scan)** `SessionGuard.tick` returns early when any window other than the main one is showing, so a locked account stays logged in for as long as an
        order-history or report window stays open. It is still re-checked on screen switches, payments and admin actions, so this is a short gap, not a hole. **(confirmed)**
15. [ ] **[Low] The phone pattern accepts 11 digits.** **NEW (3rd scan)** `ValidationUtil` allows `0` or `84` followed by 9 or 10 digits, so `0` plus 10 digits passes. Current Vietnamese mobile numbers are `0` plus 9 digits; the 10-digit tail only fits old landlines. A typo with one extra digit is accepted and becomes a new customer.
        Decide whether landlines count. **(confirmed)** **Reproduced in the 6th scan:** `isValidPhone("01234567890")` = true.
16. [ ] **[Low] A password may equal the username.** **NEW (3rd scan)** `isValidPassword` only needs 6 characters with a letter and a digit, so `admin123` for the user `admin123` is accepted. Reject a password that contains the username, and the default `Admin@123`
        (already rejected in the first-login prompt, but not when an admin resets another account). **(confirmed)** **Reproduced in the 6th scan:** `isValidPassword("admin123")` and `isValidPassword("Admin@123")` are both true.
17. [ ] **[Low] Cash received and change are never stored.** **NEW (3rd scan)** The payment dialog works out the change, but the order keeps only method, discount and total, so a shift's cash cannot be reconciled afterwards (needed by feature 4.6). **(confirmed)**

18. [ ] **[Med] Vietnamese text can be stored two ways, and uniqueness is case-sensitive.** **NEW (4th scan)** There is no Unicode normalisation anywhere (no `Normalizer` use). The same word typed with composed or separate accent marks ("Trà") looks identical but is different text,
        so `UNIQUE` on category names and usernames lets visually identical duplicates in, and searches miss them. `Trà` and `trà` are also two different categories. Normalise text to NFC on input and make the unique checks case-insensitive (after looking for existing duplicates). **(confirmed: search code and constraints read)** **Reproduced in the 6th scan:** `Trà` written composed, `Trà` written with separate accent marks, and `trà` were all accepted as three categories (the first two print identically but `equals` is false).
19. [ ] **[Low] A product can be saved with a negative cost, or a cost above its price.** **NEW (4th scan)** The product dialog checks that price is above 0 and stock is not negative, but not the cost (`AdminController`, around line 1302). Reject a negative cost and warn when cost is higher than price. **(confirmed)** **Reproduced in the 6th scan at the DAO level:** a product with cost -5000 and price 1000 was saved; the dialog's own check was not run (it needs the screen).
20. [ ] **[Low] Esc throws away a half-filled form.** **NEW (4th scan)** Since Esc was bound to Cancel in every dialog, pressing it by accident in the product or account form discards everything typed, with no question. Ask only when something was changed. **(inferred from the key binding)**
21. [ ] **[Low] One low-stock number for every product.** **NEW (4th scan)** `ProductDAO.LOW_STOCK_THRESHOLD` is 10 for everything: too low for a fast seller, too high for a slow one. See feature 4.19. **(confirmed)**

22. [ ] **[Med] Two OPEN orders on one table are not prevented, and the table map then picks one at random.** **NEW (5th scan)** `TableDAO.findAll` joins `(SELECT id, table_number FROM orders WHERE status='OPEN' GROUP BY table_number)`; with two open orders on the same table the bare `id` column is arbitrary, so the table map and the order you open may differ from the one the cashier just edited.
        Nothing in the schema stops a second OPEN order for a table (only the POS flow avoids it). Check the data for duplicates, then add `CREATE UNIQUE INDEX ... ON orders(table_number) WHERE status = 'OPEN'` and make `OrderDAO.insert` return a clear message when it is hit. **(confirmed in code; the duplicate itself not reproduced)** **Reproduced in the 6th scan:** two OPEN orders for table 7 (ids 2 and 3) were created with no error, `TableDAO.findAll` reported order **2** for that table while `findOpenOrderByTable(7)` returned order **3**: the table map and the order that opens disagree.
23. [ ] **[Med] "Which day is a sale?" has three different answers.** **NEW (5th scan)** Extends 3.5. `ReportDAO.summary` uses `COALESCE(paid_at, order_date)`, `topProducts` and `dailySales` use `paid_at` only, the order history filters by the created date, and the dashboard's "customers today" counts by `order_date` and includes unpaid OPEN orders while its revenue uses `paid_at`.
        On a day with an open order or a sale past midnight, the report summary and its own table can disagree with each other, and with the dashboard. Pick one rule (paid date for money, created date only for open orders), put it in one SQL fragment, and add a test with a sale that crosses midnight. **(confirmed by reading the queries)** **Reproduced in the 6th scan:** a PAID order with no `paid_at` is counted by `summary` (1 order, 40,000đ) and missing from `dailySales` (empty list); a sale ordered 20/01 23:50 and paid 21/01 00:10 shows in the history for 20/01 but in the report for 21/01.
24. [ ] **[Med] The last autosave can be lost when the window is closed.** **NEW (5th scan)** Autosave goes through `Async.runOrdered`, whose thread is a daemon, and `OrderController.confirmLeaveOrder()` just removes the close guard and returns `true` (no flush, no question). If the cashier closes the window right after changing the cart, the JVM can exit before the queued save runs, so that last change is gone. SQLite stays consistent (no corruption), the order just misses the last line.
        On close, wait for the ordered queue (for example `ORDERED.shutdown()` then `awaitTermination` a couple of seconds) before exiting. **(inferred from the code; not reproduced)** **Mechanism reproduced in the 6th scan in a plain JVM:** a 400 ms job queued on `Async.runOrdered` never ran when `main()` returned (the file it would write did not exist at exit). Not tried in the real window, so the real window's timing is still untested.
25. [ ] **[Low] A paid order's loyalty points are taken back with today's rule.** **NEW (5th scan)** `cancelPaidOrder` recomputes the points to remove from `LoyaltyPolicy.pointsFor(total)`; payment also used the policy of that day. If the points rule ever changes, cancelling an old order removes a different number than was given. Store `points_earned` on the order at payment (see 3.7 and 4.16) and take back exactly that. **(confirmed by reading)**
26. [ ] **[Low] An empty-looking database is accepted as a new shop.** **NEW (5th scan)** `initialize()` decides "first run" by whether the `users` table exists. A zero-byte `lunavera.db` (which bug 2.23 can create) therefore passes as a brand-new install: the default admin and the starter menu are seeded again and the old data is gone without any message. Treat a zero-byte file as damaged: say so and point to the backups folder. **Reproduced in the 6th scan:** starting against a 0-byte `lunavera.db` gave 1 admin account and 33 starter products and no warning.
27. [ ] **[Low] A customer typed at the till is created even when the payment then fails.** **NEW (6th scan)** `OrderController.completeOrder` calls `ensureCustomerInDb` first and only then the payment transaction. If the payment fails (not enough stock, order already closed), the new customer row stays, with 0 points and no orders. Harmless, but it pollutes the customer list; create the customer inside the payment transaction (service layer, 6.21). **(confirmed in code)**
28. [ ] **[Low] A late autosave is silently ignored.** **NEW (6th scan)** `OrderDAO.saveOrUpdateOpenOrder` returns the order unchanged when the order is no longer OPEN (rolled back; the comment says this is on purpose). The screen cannot tell: if another till or an admin empties the table (edge case 3.8), the cashier keeps adding lines that are never saved and only learns at payment ("không còn ở trạng thái đang mở"). Return a flag, and show "Đơn này đã bị đóng ở nơi khác" at once. **(confirmed in code)**
