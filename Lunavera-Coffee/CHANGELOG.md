# Changelog

What each version of Lunavera Coffee changed, for the owner and for whoever keeps an old version for a week
(`docs/RELEASE.md`, step 4). One section per `git tag`, newest first, in the form [Keep a Changelog](https://keepachangelog.com/).

**No version has been tagged yet** (`pom.xml` still says `1.0-SNAPSHOT`), so everything built so far is under
*Unreleased* below. It is a summary by theme, not a list of commits: the numbered detail (what was done, how it was
checked, what is still open) is in `TODO.md` (the item numbers in brackets) and `progress.md` (one entry per session).
None of it has been run through `./mvnw -B clean test` by the owner or tried on the shop's real tills yet; see the
"Release status" block at the top of `progress.md`.

## How to add a version

1. When a release is ready (`docs/RELEASE.md`, steps 1 to 4), rename *Unreleased* to the version and the date, for example
   `## [0.9] - 2026-11-03`, and put a new empty *Unreleased* heading above it.
2. Use only these headings: **Added**, **Changed**, **Fixed**, **Security**, **Removed**. Leave out the ones with nothing.
3. Write what a person at the till or the owner would notice, in one line each. Say when a version **upgrades the
   database** (`schema_version` / `user_version` changes): an older version then refuses the data (`docs/RELEASE.md`, step 5).
4. Tag the same commit with the same name (`git tag v0.9`).

- **Invisible characters from Zalo and phone contacts** (3.71): a phone number, e-mail, amount, voucher code, number of points, name or search pasted with a non-breaking space, a zero-width space or a left/right mark is now read as the person meant it, instead of being refused with no hint why (or being saved as a different name). `+84 (0) 901 111 222` and `+840901111222` are accepted as `0901111222`. ### Security
- **Expenses, vouchers, the transfer QR and the shop settings now leave a line in the audit log (TODO 2A.44).** Writing down an expense or cash taken from the drawer, deleting an expense (the line keeps the amount, category, day and note), making a voucher code, switching one on or off, choosing or accepting the bank-transfer QR, and changing the shop name, address, phone, tax code, low-stock level or day start are all shown in the audit window, in both languages. Each line is saved together with the change itself.
- **Gift-card codes can no longer be tried without limit (TODO 2A.45).** Every unknown code typed on a till is counted and written to the security log; after 5 in a minute the gift-card lookups on that till pause for 60 seconds ("Too many unknown gift-card codes. Wait N seconds.") and one line in the audit log says so.
- **A colleague's PIN can no longer be switched off in silence (TODO 2A.46).** When five wrong PINs for one name switch a PIN off, the audit log now gets a line (who was signed in on the till, how many wrong PINs), and the owner of the PIN sees "Your PIN was switched off" once at their next sign-in. Each till also counts wrong PINs for all names together: after 10 in a row the PIN pad of that till is closed for 15 minutes and the password of the person signed in opens it, so one till cannot switch off everybody's PIN.
- **Easy passwords and PINs are refused (TODO 2A.47).** A new password may no longer be one of about 4,000 commonest passwords, one repeated character, a keyboard run like `qwertyuiop1` or `1q2w3e4r5t`, or a common word with a year (`letmein7777`, `admin2027!`, `caphe2030`). A new PIN may no longer be `121212`, `123123`, `112233`, `000111`, `696969`, `123321`, `147258` and similar. Passwords and PINs already set keep working; the rules apply when one is created or changed.
- **The database guide now gives the app's user only the rights it uses** (TODO 2A.36): `SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES, TRIGGER, LOCK TABLES` on its own database, not `ALL PRIVILEGES`, so a stolen till or a leaked `database.properties` cannot drop the tables. Checked on a real MariaDB server: tables created, an older database upgraded, a sale and a backup all work with it.
- Passwords are hashed with PBKDF2 at 600,000 iterations; an older hash is upgraded at the next successful login (2A).
